# v0.4.8 生产升级修复

## 修复范围

v0.4.7 的启动检查误将历史短密钥站点阻止在旧库校验之前。本版修复这个兼容性回归，不包含其他功能迭代。

- 保留原 `JWT_SECRET`，存储密钥、SMTP 密码和待发送邮件继续用原密钥解密，不重写已有加密内容。
- 旧库及原密钥通过校验后，弱密钥站点自动生成 32 字节随机登录签名密钥，JWT 和验证码均使用新签名。旧登录失效，账号密码不变。
- 强密钥站点继续使用原签名密钥，不强制注销。全新安装仍要求强密钥。
- 缺失、错误的原密钥仍然拒绝启动，不会猜测旧密钥或清空配置。
- 数据库结构版本仍为 9，不新增表或字段。若来自 v0.4.6，仍会补充 v0.4.7 已引入的 `installation_key_digest` 设置，不覆盖现有设置。

## 覆盖步骤

1. 停止程序，备份数据库、程序目录、原 `.env`、整个 `data/` 及所有自定义图片/背景/Logo 路径。
2. 按 VPS 架构选择 `linux-amd64` 或 `linux-arm64` 包，先解压到新目录。对照外部 SHA256 清单核对压缩包；进入解压目录运行 `sha256sum -c SHA256SUMS` 校验文件。
3. 将包内 `zhuapic` 和 `static/` 内容合并覆盖到原工作目录，不删除旧 `static/assets/site-*` 自定义文件。包不包含 `.env`、数据库、图片或站点私有配置。
4. **不要修改或重新生成原 JWT_SECRET，不要覆盖 .env，不需要重新安装。** 保持服务原工作目录，确认服务用户可以在 `data/` 写入文件。若指定了 `INSTALL_CONFIG`，应允许写入该配置的父目录。
5. 启动程序并检查日志、`/api/ready`、重新登录、旧图及后台已有设置。无需测试发送真实邮件或修改存储配置来完成此次升级。

独立签名密钥默认位于 `data/installation.json.session-key`，自定义路径时为 `${INSTALL_CONFIG}.session-key`，权限 0600。该文件自动生成且不打印密钥内容。请将它与原 `.env` / 安装文件一起保密备份并持久化。多实例必须共享此文件，首次升级请先单实例启动；文件系统须支持原子硬链接。

如果仍提示原密钥缺失/不匹配，请恢复部署前的原 `.env` 或安装配置，并核对服务工作目录。**不要把密钥发到聊天中。** 文件权限或数据目录只读报错需修正服务用户权限，不要改为 0777。

## 限制与回退

本次没有轮换历史数据的加密密钥。弱加密密钥的历史风险仍存在，后续需在完整备份及凭据轮换流程中处理。

回退需停服、恢复对应旧程序和静态文件，保留原配置及数据。不要删除新签名密钥文件，便于再次升级保持会话稳定。回退到使用弱密钥签名的老版本会重新暴露旧的登录签名风险，因此只作为短时应急措施。Docker 镜像另行发布。
