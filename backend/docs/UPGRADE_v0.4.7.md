# v0.4.7 生产覆盖升级

## 这次是否改变数据库结构？

从 v0.4.6 升级：没有新增表、字段或结构版本，仍为 schema 9。启动时会新增 `site_settings.installation_key_digest` 设置，用于核对原加密密钥；不会重设已有管理员、页面内容、存储路径、用户组或 SMTP 设置。

从更早版本升级：会补跑之前尚未执行的迁移，可能新增表和字段。必须先备份数据库，不要把本说明理解为所有旧版本都没有结构变更。

## 升级包内容

- `zhuapic`：Linux 静态二进制，保留旧程序文件名，服务配置通常无需改名。
- `static/`：新版前端，包含首次部署安装页。
- `UPGRADE.md`、`README_DEPLOY.md`、`docs/INSTALLATION.md`：升级与安装说明。
- `BUILDINFO.json`、`SHA256SUMS`：构建信息和包内文件校验。

不包含 `.env`、`data/`、数据库、用户头像、图片、密钥或自定义 Logo/背景。不要用“清空目录再上传”或带 `--delete` 的同步方式部署。

本次发布使用 Go 1.27.1 构建，并将间接依赖 `filippo.io/edwards25519` 更新到 1.1.1，修复 [GO-2026-4503](https://pkg.go.dev/vuln/GO-2026-4503)。不要求在生产服务器安装 Go。

## 升级前检查

1. `uname -m` 为 `x86_64` 时选 amd64；为 `aarch64` 或 `arm64` 时选 arm64。不要混用。
2. 备份数据库、旧 `zhuapic`、完整 `static/`、`.env` / `installation.json` 及所有数据目录。保存原 `JWT_SECRET`，不得临时换一个新值。
3. 原密钥应至少 32 字符，不能是示例或明显弱密钥；不符合时新版会拒绝启动。不要直接换密钥绕过，否则旧存储和邮件凭据无法解密。需另行处理安全轮换。
4. 数据库连接池 `DB_MAX_OPEN_CONNS` 不得小于 2。原 `.env` 的数据库连接、路径和 `BASE_URL` 保留，不替换为示例配置。
5. 若 Nginx 在本机通过 `127.0.0.1` 代理到程序，在原 `.env` 增加 `TRUSTED_PROXIES=127.0.0.1/32,::1/128`；若代理在其他机器/容器，填写实际代理地址。不要信任所有地址或整个私网。代理应正确设置 `X-Forwarded-Proto`，并清理客户端伪造的转发头。
6. 运行用户需可写 `data/site-assets`（或指定的 `ASSET_DIR`）。旧 `static/assets/site-logo-*`、`site-background-*` 必须保留，程序启动时复制到持久化目录，原 URL 不变。
7. 自定义图片资源的 `/assets/site-*` 请求需经 Go 服务。若 Nginx 将所有 `/assets/` 直接映射为静态目录，应为 `/assets/site-logo-*` 与 `/assets/site-background-*` 增加更优先的反代规则。否则更新背景后可能出现 404。

仅当本机 Nginx 当前确实反代到 `127.0.0.1:8080` 时，可以参考以下单独 location；不同端口和拓扑需对应修改：

```nginx
location ~ ^/assets/site-(logo|background)- {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

若现有静态规则使用 `location ^~ /assets/`，它会跳过上述正则规则，必须调整该优先级，或让整个 `/assets/` 经过 Go 服务。修改后先运行 `nginx -t`。

## 覆盖顺序

1. 在临时目录解压升级包，进入包内目录，运行 `sha256sum -c SHA256SUMS`。
2. 停止原服务/进程，避免直接替换正在运行的二进制。
3. 将包内 `zhuapic` 覆盖到原位置并确保可执行；将 `static/` 的内容**合并覆盖**到原 `static/`，不要删除旧自定义文件。说明文件可一并复制。
4. 确认运行用户、工作目录和原 `.env` 未改变，启动原服务。已有环境配置会继续直接进入站点，**不需要进入安装页，也不需要重填数据库**。
5. 查看启动日志，检查 `/api/ready` 返回 200；登录管理员，确认页面配置、背景、旧图链接、存储名称和用户组正常。后台版本应显示 v0.4.7。
6. 如需测试上传，使用可删除的小测试图片；不要通过修改生产管理员密码、批量同步或真实邮件群发来验证升级。

已有 `.env` 部署的后台任务保持原开关。只有通过安装向导“接入旧库”时才默认暂停后台任务，二者不要混淆。

## 失败与回退

- 如果已有站点出现安装页，先停止程序，检查工作目录、`.env`、环境变量和挂载；不要在生产库重新初始化。
- 如果密钥检查、权限或数据库连接失败，保留原库和原密钥，先修复日志指出的问题，不要删除数据表或安装配置。
- 从 v0.4.6 升级失败时，可停止新版、恢复已备份的旧二进制与 static，保留原 `.env` 和数据。新增密钥摘要对旧版无影响。若新版已更换自定义资源，应同时保留/恢复相关资源及设置。
- 从更早版本升级涉及结构迁移时，回退必须同时考虑升级前数据库备份，不能仅回退二进制。
