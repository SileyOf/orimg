# 安装与旧库接入（v0.5.0）

Docker 部署首先阅读 [Docker 指南](DOCKER.md)，特别是反向代理与已有数据挂载要求。

## 首次安装

1. 准备 MySQL 数据库及专用账号。数据库应先由数据库管理员创建；安装账号需要该库的读写、建表、索引及 ALTER 权限，不需要全局管理员权限。
2. 将程序和 `static/` 放在同一个工作目录。持久化整个 `data/`，或分别指定 `INSTALL_CONFIG`、`UPLOAD_DIR`、`CACHE_DIR`、`ASSET_DIR`。配置文件的父目录必须可写。
3. 首次使用不要设置 `DB_HOST`、`DB_USER`、`DB_NAME`、`JWT_SECRET`，也不要复制旧站点 `.env`。可以使用新版 `.env.example`，其中数据库配置均为注释。
4. 启动程序后访问 `/install`，输入服务器日志中的一次性安装码。远程安装必须使用 HTTPS；HTTP 仅允许本机回环地址，可通过 SSH 端口转发访问。
5. 填写数据库连接和站点地址，检查连接。此步骤只读。默认使用 TLS 且验证证书；仅隔离的本机/容器网络才选择不使用 TLS。自签 CA 可粘贴 PEM，证书仍需匹配数据库主机名。
6. 空库填写管理员用户名、邮箱和至少 12 字节的密码。确认后创建表、管理员及对应用户组。没有固定初始密码，签名/加密密钥由系统随机生成。新站点默认关闭游客上传，登录后可上传；已有站点的游客上传设置保持不变。

安装完成后无需重启，安装 API 和页面关闭。重启不会重开安装入口。安装码仅存在于当前进程，重启会生成新的安装码。`/api/health` 表示进程存活，`/api/ready` 仅在安装完成且数据库可连接时返回 200。

## 用新程序接入旧数据库

这是保留数据的重新部署基础，**不是文件搬迁、导入或导出工具**。

1. 先备份旧库、原 `.env` 或 `installation.json`、图片原文件、自定义背景和 Logo。保留原 `JWT_SECRET`；存储密码和待发送邮件可能使用它加密。
2. 停止旧程序及后台工作器，避免两个部署同时处理任务。将旧图片目录、NAS 挂载及本地副本放到新环境的相同路径。配置存在库内的自定义路径不会被安装器改写。
3. 新工作目录以未安装状态启动，在向导中选择旧数据库。系统识别结构版本，要求原有效管理员邮箱、密码及原 `JWT_SECRET`，不会创建第二个管理员，也不会根据用户名自动提升权限。
4. 验证通过后补齐缺失结构，保留账号密码、用户组、站点文案、存储及 SMTP 配置。默认暂停邮件、同步、备份与清理任务；确认挂载及配置后设置 `DISABLE_BACKGROUND_WORK=false` 并重启启用。
5. 验证登录、旧图、背景、存储路径及队列，再切换正式流量。接入本身不访问云存储、不发邮件、不复制图片。

v0.4.6 数据库的结构版本仍为 9，本版不增加结构迁移，只新增一条 `installation_key_digest` 设置来校验原密钥（摘要不是可还原密钥）。更老数据库会执行此前缺失的结构迁移。检测到更高版本或不认识的非空库会拒绝接入。没有有效管理员的旧库需先恢复原账号，不会自动绕过验证。

首次安装仍拒绝弱密钥、示例密钥及少于 32 字符的密钥。v0.4.8 修复旧站点升级兼容性：确认旧库及有效管理员、校验原密钥后，保留原 `JWT_SECRET` 解密既有凭据，并为弱密钥站点生成独立的随机登录/验证码签名密钥。已有弱密钥签发的登录会失效，需要重新登录；账号密码不变。**不要直接更换旧库 JWT_SECRET**。这不是加密数据轮换，历史弱加密密钥的风险仍需在后续专门轮换时处理。

## 配置持久化与失败恢复

- 默认 `data/installation.json` 使用 0600 权限原子写入，包含数据库密码和原始加密密钥，应像 `.env` 一样保密并离线备份。管理员明文密码不会写入该文件。
- 独立签名密钥保存在 `${INSTALL_CONFIG}.session-key`，默认 `data/installation.json.session-key`，权限 0600。即使仍使用 `.env` 部署，也使用此路径；其父目录必须允许服务用户写入。应与原配置一起持久化、保密备份，不能打入镜像。多实例必须共享同一密钥文件并使用原子硬链接可用的文件系统；首次升级建议停服后单实例启动。文件损坏或权限过宽会停止启动，不会静默替换。丢失文件会生成新签名密钥并使旧登录失效，不影响原加密数据，但不能把删文件作为日常升级操作。
- 进行数据库变更前先写安装检查点。中断后保留该文件及数据库，重新启动并用同一数据库、当前安装码继续。若管理员已经创建，需重新验证原管理员。
- MySQL DDL 可能部分提交，不能承诺整次升级事务回滚。不要删表重试，也不要删除未完成安装的检查点或替换密钥。
- 配置损坏、密钥不匹配、旧库连接失败会停止启动，不会自动退回公开安装状态。
- 已有环境变量部署仍可使用原 `.env` 启动，不强制转换。空库的环境变量部署必须明确配置强密钥和管理员邮箱、密码；已有用户不会被重设。
- 有安装文件时以文件内容为准，仅 `PORT`、`TRUSTED_PROXIES`、`DISABLE_BACKGROUND_WORK` 可由环境覆盖。修改数据库地址需在停机并备份配置后更新安装文件。

## 代理、文件与备份

- 明确设置 `TRUSTED_PROXIES` 为实际代理 IP/CIDR，代理需覆盖而非透传客户端提供的 `X-Forwarded-*`。默认不信任任何代理，包括内网地址。不要配置 `0.0.0.0/0`。
- 自定义 Logo/背景改存到 `ASSET_DIR`，原 `/assets/site-*` URL 不变。旧 `static/assets/site-*` 文件启动时复制保留；部署前仍应备份，不能先删除旧资源。反向代理应将这些路径交给 Go 服务，不能全部绕过服务直接映射只读 static 目录。
- 数据库备份在 `DB_TLS=verify` 时使用 MySQL `mysqldump --ssl-mode=VERIFY_IDENTITY`，可用自定义 CA；不支持该参数的客户端会报错，不会退回明文。镜像需包含兼容 MySQL 客户端和系统 CA。
- 数据库备份不包含安装配置、原始密钥和图片文件；三者应分别备份。Docker 镜像从 v0.5.0 提供，自动恢复工具及多节点部署仍属后续范围。
## 隔离回归

`go test ./...` 默认不连接数据库。完整安装回归仅接受 `ORIMG_INSTALL_TEST_PORT` 指定的回环端口，并要求新建空库 `orimg_install_test`，使用固定的测试专用密码。测试会创建 `orimg_install_resume`，只能在一次性本地容器中运行，禁止指向任何共享库。测试不启动邮件、云存储或清理工作器。
