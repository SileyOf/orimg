# Docker 与开源发布前初审

审查日期：2026-09-24。源码版本：v0.4.6。

> 历史记录：以下发现及“未完成”描述以当时版本为准。v0.4.8 已加入旧密钥兼容，v0.5.0 已交付 Docker；当前情况见 [Changelog](../../CHANGELOG.md)。2026-11-16 的源码整理不是重新完成全面安全审计。

## v0.4.7 跟进

以下 R1-R10 是 v0.4.6 的历史发现。本轮已实现对应的代码加固：一次性安装码与无默认凭据、禁止启动时提升账号、GIF 帧探测与缩略图预算、初始管理员分组、独立持久化资源、显式代理信任、数据库安装锁、优雅退出与 readiness、可校验的 MySQL TLS、请求体期限与上传并发限制。

新增 `/install`，支持空库初始化和验证原管理员/密钥后接入旧库。配置使用私有原子检查点，安装完成关闭入口，损坏配置不会重新开放安装。新库默认关闭游客上传，旧配置不覆盖。详见 [安装与旧库接入](INSTALLATION.md)。

验证包括 Go 单元/竞态测试与静态检查、Linux amd64/arm64 编译、全新本机 MySQL 8.4 临时库的初始化/旧库逐表保留/错误密钥/中断恢复/并发启动，以及 390/768/1440/2560 宽度的安装向导模拟流程。没有访问生产库、真实 SMTP 或云存储。

这不等于完整安全认证。正式 Docker 发布前仍需升级构建工具链、执行 govulncheck/镜像扫描、验证真实数据库 TLS/备份恢复、固定构建依赖并完成许可证和源码秘密扫描。本轮只增加构建上下文排除规则和更新安装文档，没有发布镜像或开源仓库。

## 历史审查范围

本轮为静态审查与本地检查，不是完整安全审计。没有连接生产库、测试库、SMTP 或对象存储；没有执行数据库迁移，没有修改业务代码、账号或配置。

结论：可以进入发布加固阶段，但不建议把当前工作目录直接制作成公开镜像或源码包。优先修复初始化、安全默认值和持久化边界，再完善构建与发布流程。

## 源码发现

### R1 [P1] 缺少配置时使用公开 JWT 密钥和弱管理员密码

- 位置：`config/config.go:73`、`config/config.go:85`、`.env.example:17`。
- `JWT_SECRET` 缺失时使用固定字符串，首次管理员密码默认为 `admin`，示例也使用该密码。空环境变量同样没有被启动校验拒绝。
- 新部署遗漏配置仍会启动。固定密钥可被用于签发会话；该密钥同时参与存储与邮件凭据加密，影响不只登录。
- 建议：启动时拒绝空值、示例值及明显弱密钥；首次安装要求显式初始化管理员凭据或一次性安装流程。既有强密钥必须保留，不能为了镜像升级自动重新生成，否则旧加密配置无法解密。

### R2 [P1] 启动会自动提升普通用户权限

- 位置：`database/database.go:396`、`:413`、`:423`。
- 当没有启用中的管理员时，启动代码会把配置用户名对应的用户提升为管理员并启用；找不到时提升最早的用户。
- 这会在容器重启时改写权限与禁用状态。恢复管理员不应由普通启动根据用户名或注册顺序推断。
- 建议：仅空库执行首次管理员创建；已有库缺少管理员时明确报错或进入受限恢复状态，通过显式运维命令恢复，并记录审计。

### R3 [P1] GIF 动图判断会完整解码所有帧

- 位置：`utils/images.go:272`、`:283`；调用点 `handlers/app.go:465` 附近。
- 小于 32 MB 的 GIF 会进入 `gif.DecodeAll`。上传文件大小和逻辑画布尺寸限制不能约束所有帧累计解码内存，也没有全局解码并发上限。
- 高压缩、多帧图片及并发上传可能导致内存陡增，触发容器 OOM。此轮没有运行大内存攻击样本。
- 建议：使用有界的格式解析检测帧数，不为动图判断保留所有像素；限制累计帧像素、解码内存及并发。缩略图解码也应纳入同一资源预算。

### R4 [P2] 全新安装的管理员没有用户组

- 位置：`database/database.go:33`、`:36`、`:390`；`database/migrations.go` 的 `migrateUploadPolicies`；`handlers/policies.go:369`。
- 用户组迁移先执行，给当时已有用户分组；随后创建管理员的 INSERT 没有写入 `group_id`。空库中此时没有用户可供迁移分组。
- 当前权限模型明确禁止未分组账号上传，包括管理员。新安装后直接上传会被拒绝。
- 建议：首次创建管理员时在事务内绑定首次安装创建的组。不要通过每次启动给所有未分组用户自动补组来修复，否则会破坏管理员主动取消分组的操作。
- 需要新增真正从空库开始的安装测试，而不只是已有测试库上的升级测试。

### R5 [P2] 自定义资源写入程序静态目录

- 位置：`handlers/app.go:302`、`handlers/background.go:84`、`routes/routes.go:103`。
- Logo 和背景图片写入 `static/assets`，与镜像中的 JS/CSS 混放。仅持久化 `data` 后，重建容器会丢失这些文件；挂载整个 assets 目录又可能遮住镜像升级的新前端资源。
- 建议：独立持久化自定义资源目录和服务路由，静态程序资源只读。保留旧 URL 的兼容读取，提供显式、可验证的旧文件迁移，不擅自改写生产路径。

### R6 [P2] 反向代理信任范围过宽

- 位置：`handlers/app.go:1353`。
- 来自任意私网、回环或链路本地地址的请求，都信任 `X-Forwarded-For` 的最左值。共享容器网络中可直连应用的其他容器，或追加而非覆盖该头的代理，可让客户端控制限流和审计所用 IP。
- 建议：配置明确的可信代理 CIDR，按可信代理链解析来源；默认不信任转发头。Compose 示例只向代理开放应用服务，并明确代理的头部覆盖规则。

### R7 [P2] 数据库迁移没有跨实例互斥

- 位置：`database/migrations.go:34`、`:42`、`:50`；`database/database.go:201`。
- “检查字段/迁移版本再执行 DDL”的流程没有迁移锁。两个应用实例同时冷启动或升级时，可同时认定迁移未执行，随后发生重复字段、索引或迁移记录冲突，导致启动失败。
- 建议：覆盖基础建表、版本迁移和首次初始化的数据库互斥锁，或者独立迁移命令先于应用启动执行。不要把 MySQL DDL 的事务包装理解为完整可回滚迁移。
- 第一版 Docker 明确只支持单应用实例，后续再验证多副本与共享存储行为。

### R8 [P2] 容器退出和就绪状态未完成

- 位置：`main.go:24`、`:35`、`:42`；`routes/routes.go:23`。
- 后台任务使用不可取消的 Background context，未处理 SIGTERM，也没有调用 Server.Shutdown。容器停止时无法主动停止领取任务并等待在途请求。
- `/api/health` 固定返回成功，适合作为进程存活信号，但不能判断数据库故障或迁移就绪状态。
- 建议：共享可取消上下文、有限时长的优雅退出、工作器退出等待；分开 liveness 与 readiness，并为数据库就绪检查设置短超时。

### R9 [P2] 数据库连接无法配置 TLS

- 位置：`database/database.go:18`、`config/config.go:25`。
- DSN 直接拼接，未设置 TLS，也没有 CA/服务端名称配置入口。连接远程 MySQL 时，不能按部署要求启用并验证 TLS；驱动默认不启用 TLS。
- 建议：使用驱动 Config/FormatDSN 构造连接，提供证书校验、连接及读写超时配置。部署文档区分同机隔离网络和跨主机连接，不使用跳过证书验证的“安全”示例。
- 参考：[MySQL 驱动 TLS 参数](https://github.com/go-sql-driver/mysql#tls)。

### R10 [P2] 上传接收阶段缺少读取期限

- 位置：`main.go:38`、`handlers/app.go:353`、`:377`。
- 服务仅设置 ReadHeaderTimeout；ParseMultipartForm 在 15 分钟业务 context 建立之前执行，慢速请求体可持续占用连接、goroutine 和临时文件。context 超时本身也不等同于请求体读取 deadline。
- 建议：为上传接收设置明确的读取期限和并发限制，配合反向代理的 body timeout 与大小限制。大文件下载不应简单套用过短的全局写超时。

## 发布准备缺口

1. **构建上下文隔离**：工作目录存在 `.env`、`data`、缓存及历史 `dist`，没有 `.dockerignore`。`.gitignore` 不能代替 Docker 的忽略规则；镜像应只复制明确需要的源码和资源。当前没有镜像，因此这里是发布风险，不是已泄露镜像的结论。[Docker 文档](https://docs.docker.com/build/concepts/context/#dockerignore-files)
2. **工具链更新**：本机检查使用 Go 1.23.1，`go.mod` 为 1.23.0。该系列已不在官方支持窗口。正式镜像改用受支持版本的补丁版，重新测试并运行 govulncheck、镜像漏洞扫描，记录 SBOM；本轮没有做完整 CVE 扫描。[Go 支持政策](https://go.dev/doc/devel/release#policy)
3. **运行依赖**：`storage/coordinator.go:433` 依赖外部 `mysqldump`。只放静态 Go 二进制的镜像不能完成数据库备份。需要兼容目标 MySQL 的客户端、CA 证书，以及经过确认的时区设置。
4. **测试可复现**：部分集成测试硬编码当前测试库主机；浏览器测试依赖未锁定的 Playwright、系统 Chrome 和 `/tmp/orimg-email-preview.html`。改成一次性本地 MySQL、假 SMTP/对象存储服务，补 Node 依赖锁文件和统一测试入口，保留拒绝连接非测试数据库的保护。
5. **源码净化**：测试中仍有个人邮箱、部署域名和测试服务器地址。改用 `example.test` 等测试资料，不直接公开现有工作目录。有限模式扫描未检出需要在报告中披露的真实令牌，但不代表完成全量秘密扫描；`.env` 未读取或输出。
6. **开源元数据**：当前目录不是 Git 仓库，未发现项目级 LICENSE、SECURITY.md、CONTRIBUTING.md 或 CI 配置；已存在 Lucide 许可证。根 README 仍描述 v0.1.0-beta.4 和已删除的 Full 模式。先确定项目许可证与品牌素材许可范围，补齐归属和依赖许可清单，再建立干净的公开仓库。

## 建议实施顺序

1. 发布加固：处理 R1-R10，优先安全默认值、初始化及持久化；保持现有强密钥、账号、图片 URL 和生产存储设置不变。
2. 容器交付：单应用实例 + MySQL 的 Compose 示例；多阶段构建；非 root；程序只读、数据独立挂载；支持 linux/amd64 与 linux/arm64；运行凭据仅在运行时注入。
3. 安装与升级验收：空库安装、旧库升级、重复启动、暂停/重启任务、替换镜像后自定义资源保留、数据库断开后的 readiness，以及备份恢复演练。
4. 开源整理：Origin 项目名与 Origin 站点品牌边界、README、许可证、贡献与安全报告说明、CI、版本标签、校验和和依赖清单。

不需要为了容器化重建数据库或更换数据库引擎。初始化和迁移锁主要是代码修复；自定义资源路径调整需要先设计兼容迁移。若后续需要数据库结构变更，应单独列出迁移脚本、影响与回滚/恢复方案，再执行生产升级。
